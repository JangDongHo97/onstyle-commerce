## 설계 결정과 이유

<!-- 이 섹션이 사실 가장 중요합니다. "왜 이렇게 했는지" 설명하는 자리라,
     면접 PT에서 그대로 쓸 수 있어요. 기능 하나 끝날 때마다 한 항목씩 추가하세요. -->

### Category 계층 구조: Adjacency List vs Closure Table
**결정**: Category의 자기참조 계층 구조를 Adjacency List(자기참조 FK, `parent`/`children`)로 구현했습니다. Closure Table, Materialized Path도 검토했습니다.

**이유**: 카테고리 깊이가 얕고(대/중/소 3단계 수준) 구조 변경이 드물어서, 하위 카테고리 조회 시 재귀 비용이 크지 않다고 판단했습니다. 반면 Closure Table은 하위 트리 전체 조회가 빨라지는 대신 별도 테이블과 INSERT/DELETE 관리 로직이 추가로 필요해서, 이 프로젝트 규모에서는 이점보다 복잡도가 더 크다고 봤습니다.

**트레이드오프**: 만약 대규모 트래픽 환경에서 하위 카테고리 전체 조회가 매우 빈번한 서비스였다면, 재귀 쿼리 비용을 줄이기 위해 Closure Table을 선택했을 것입니다.

### Category 깊이 제한 검증 위치: Service vs 엔티티
**결정**: 카테고리 깊이 제한(대/중/소 3단계)은 엔티티가 아니라 Service에서 검증합니다. 등록 시 부모 체인을 따라 올라가며 깊이를 확인하고, 초과하면 예외를 던집니다.

**이유**: 검증 규칙이 바뀌어도(예: 4단계 허용) 엔티티를 건드리지 않고 Service만 고치면 됩니다. 엔티티(`addTo`)에서 검증하면 어디서 호출해도 규칙이 지켜지는 장점이 있지만, 부모 체인을 따라 올라가는 LAZY 조회가 엔티티 안에서 일어나 엔티티가 무거워지고 테스트하기 어려워집니다.

**트레이드오프**: Service를 거치지 않고 엔티티를 직접 조작하는 코드가 생기면 규칙이 우회될 수 있습니다. 카테고리 생성·이동을 Service 한 곳으로만 열어두는 것으로 보완합니다.
